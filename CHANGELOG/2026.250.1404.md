# 2026.250.1404 — docs(skills): document the mcp serve bind default + env-fallback client resolution

## Summary

Document two merged behavior changes in the `charly-mcp-cmd` skill entity's inline content (`charly.yml`, Part 1 Client + Part 2 Server):

1. **Client — env-fallback endpoint resolution.** The `mcp:` verb no longer resolves exclusively from a container's `ai.opencharly.mcp_provide` OCI label. A VM/host venue has no podman-inspectable image label, so when the label leg fails the plugin falls back to the `mcp_provide` declarations threaded in the check env (`spec.CheckEnv.MCPProvide`; `effectiveMCPProvides` in `resolve.go`) — and a VM's declared forward is threaded host-routable by plugin-check, so the dial reaches the VM's server through the forwarded port. Env-declared host-local `127.0.0.1` URLs are dialed as-is.
2. **Server — loopback-only listen default (P3).** `charly mcp serve` binds `127.0.0.1:18765` by default (loopback only; the host system is the security boundary); `--listen 0.0.0.0:18765` is the explicit opt-in, normal inside a pod/VM. The generated packages ship non-autostarting system + user systemd units plus a system-wide `/etc/charly/charly.yml`; a user-scope-unit server reads the invoking user's `~/.config/charly/charly.yml` on top of the system config (layered merge `/etc/charly` → user config → in-dir, later files winning). Child tool processes inherit the FULL environment (`childCharlyEnv` = `os.Environ()`, no `CHARLY_*` stripping).

Also corrects two stale passages that described the PRE-merge behavior: the old `childCharlyEnv` CHARLY_*-stripping claim (Architecture step 4 + auto-default) and the "fallback fires regardless of CHARLY_PROJECT_DIR" claim — the merged prefix logic (`computeProjectPrefix`) makes env vars and a cwd `charly.yml` both suppress the `--repo default` prefix.
